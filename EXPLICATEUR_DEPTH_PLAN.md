# EXPLICATEUR DEPTH PLAN v3 (backend only)

## Success definition
An explanation succeeds only when it (1) covers the essential source material for the requested
scope and depth, (2) is factually and mathematically sound, (3) teaches at the requested level,
and (4) states clearly what it did not or could not explain. Valid JSON is not success.
"Explained" is a content status, never a claim that the student has learned the material.

## Philosophy
Use as many calls as the task needs, each with one purpose (plan | vision | enrich | generate |
review | repair) under hard budgets. Waste means retries that ask the same model for a longer
answer. Preparation spend and learning spend are budgeted separately.

## Problems being fixed
P1  Course Map ranges are too coarse.
P2  One call does everything; card-level slots get filler.
P3  `covered` is word overlap plus a citation.
P4  Continue advances by part number; parts feel disconnected.
P5  Plan fingerprint depends on budget/model.
P6  Logs cannot diagnose depth (chunk_count recorded before scoping/trimming).
P7  500-chunk cap blocks Continue on large PDFs.
P8  Required migrations are ignored by Git.
P9  Extraction loses figures, flattens tables, garbles math.
P10 Tests prove plumbing, not teaching quality.
P11 Generated structural claims (e.g. which Roman numeral is which part) are never checked
    against the PDF's real headings.
P12 A skipped or failed review can still produce a success label.

## Invariants
1. Source-anchored: checklist items and course/derived claims carry page + verbatim snippet, or a
   figure/table record id, validated mechanically.
2. Scope is explicit: in_scope or skipped_by_request. Default is everything. Generating a unit
   outside the requested scope is a defect.
3. Status is earned by evidence; the generator never grades itself.
4. PDF text, figure records and retrieved passages are untrusted DATA: delimited in every prompt,
   and no stage follows instructions found inside them.
5. Never execute code generated by a model or found in a PDF (see Phase 2).
6. Logical unit identity is stable across reindex; progress is never carried over onto changed content.
7. Additive and flagged: Course Map and retrieval stay; new pipeline behind a flag.
8. Degrade, never discard: valid content survives any later-stage failure.
9. Corrections are visible and auditable; a streamed answer is never silently replaced.
10. Output language follows the selected UI language; source values are kept as written.

## Statuses
coverage_status:  explained | partial | mentioned | missing | not_generated
                  | skipped_by_request | unverifiable_source
verification:     reviewed | deterministic_only | review_failed | unchecked
confidence:       high  (reviewed, no open errors)
                  medium (deterministic_only, low-risk unit)
                  low   (high-risk unit not reviewed, or review_failed)
Rules:
- explained = all required checklist items covered AND no unresolved authoritative error.
  partial / mentioned / missing derive from checklist coverage.
- High-risk unit = has calculations or derivations, comparison claims, many numbers, exhaustive
  depth, or exercise kind. A high-risk unit without a review gets confidence low, is queued for
  review at the next opportunity, and is listed as "not independently reviewed". It is never
  presented as verified.
- Deterministic findings are tiered:
    authoritative: label-bound numeric mismatch, arithmetic recomputation mismatch, invalid anchor
      or page, structure claim contradicting the Unit Map, supplementary block overwriting a
      source value. These force partial + repair.
    heuristic: comparative-direction pattern, wording patterns. These flag the unit for review
      and never fail it alone.
- "Mastery" is not a backend status; any mastery signal must come from student interaction later.

## Provenance and claims
Block provenance: course | derived | supplementary | unverified.
- Sentence-level markers: the generator marks each factual sentence in course/derived blocks with
  source indexes (compact inline markers, parsed server-side into claims[{sentence, source_indexes}]).
- Mechanical per-claim checks: markers valid and inside the unit's pages; numbers and labels in
  the sentence bound to the cited passage.
- Reviewer per-claim check (semantic support): reports only unsupported or incorrect claims, each
  with a quote. It checks every claim in high-risk units and in scientific, medical, legal or
  numerical-conclusion content; elsewhere it checks essential claims and conclusions.
- An unsupported claim is corrected, moved into a clearly marked supplementary block, or marked
  unverified. A valid page citation on a block does not validate every sentence in it.
- Supplementary blocks (analogies, extra examples, primers for missing prerequisites) may use
  hypothetical values only when flagged hypothetical (explicit wording such as "imaginons", and
  hypothetical: true). They must never be presented as PDF facts, never reuse a source label with a
  different value, never overwrite derived values, and never invent course-specific names,
  figures or entities.

## Data model
Unit
    logical_id       hash(document_id + normalized heading hierarchy + ordinal among identical
                     sibling headings). Pages are attributes, not identity.
    content_version  hash(unit text + figure/table record hashes)
    title, heading_path, page_start, page_end
    kind             concept | derivation | worked_calculation | comparison | rule_examples
                     | figure_walkthrough | exercise | lab_step | research_finding
                     | non_teaching (transition | front_matter | summary)
    weight           estimated tokens needed
    depends_on       [logical_id]
    external_prereqs [string]
    enrichment_state skeleton | enriched
    checklist        [ChecklistItem]   (filled at enrichment)
ChecklistItem
    item_id, type (definition | formula | number_table | numeric_result | worked_calc | figure
    | code | command | question | deliverable | caveat)
    importance       essential | supporting | optional
    text, anchors [{page, snippet} | {figure_id} | {table_id}]
    expected_values  [{label_path, value}]
Figure record   figure_id, page, image_hash, caption, type, title, axes, series, key_values
                (printed values; chart-read values flagged approximate), takeaway, confidence
Table record    table_id, page, header labels, rows, confidence
PageQuality     page, text_ratio, garble_ratio, ocr_confidence, table_confidence, route
UnitProgress    logical_id, content_version_at_generation, coverage_status, verification,
                confidence, attempts, versions[]
UnitVersion     version_no, kind (provisional | verified | repaired | deepened), blocks,
                change_log[{block_id, reason_code, old_quote, new_quote, severity}]
FactsLedger     entries{kind: definition | result | notation | claim, label_path, value_or_text,
                logical_id, quote, anchor}; capped; only verified content may enter;
                selected per review by term/label overlap
LearningState   document_id, level, depth, scope_fingerprint, generated order, current/next,
                known_omissions[{logical_id, item_id, reason}], prereqs_assumed
                (compact, under ~800 tokens)

## Depth, level, importance
depth: summary | standard | exhaustive (from the prompt; "ne rien omettre" => exhaustive)
level: beginner | standard | advanced (prompt, then student profile)
Importance baseline (deterministic; the LLM may adjust with a one-line reason):
  essential   definitions; headed/bold/boxed formulas; tables and figures the text refers to;
              stated conclusions; lab commands; every exercise question and deliverable
  supporting  worked-example numbers, comparison values, illustrative examples
  optional    repeated values, asides, minor figures
Coverage required: summary = essentials in one line each; standard = essentials;
exhaustive = essentials + supporting (skipped optional items listed in the ledger);
an explicit "do not miss anything" promotes everything to required.
The reviewer judges the significance of an omission, not token counts.

## Block contracts (defaults, not rigid templates; optional blocks only when they help learning)
concept             explanation, intuition, source_example, takeaway
derivation          given, ordered steps, result, interpretation
worked_calculation  given_values, formula, substitution, result, interpretation
comparison          criteria, table, interpretation, trade_off
rule_examples       rule, sourced examples, common_error
figure_walkthrough  what_it_shows, how_to_read, specific_reading, takeaway
exercise            problem, method, working, final_answer, verification
lab_step            action, command_or_ui, expected_result, checkpoint
research_finding    evidence, interpretation, limitations
non_teaching        one line, never counts as explained
Validator: allowed block types and required blocks present; order is soft.
check_question: max 1 per unit, concept-type units only, never one already used.

## Budgets (configurable; starting values to calibrate from measurements)
PREPARATION (per document; resumable; idempotent)
  Eager at upload: deterministic parsing builds the Unit Map SKELETON (titles, pages, kinds,
    identity); page-quality report; figure candidate detection. LLM only if structure is unclear
    (heading fallback): 0-2 calls.
  Lazy, just in time (prefetch the next unit while the student reads):
    enrichment = checklist + prerequisites, batched 3-5 units per call
    vision = only for figures not recoverable from text/layout; cap 12 per document, 3 per unit;
             cached by image hash
  Typical: eager 0-2 calls; lazy about 1 call per 3-5 units plus 0-1 vision per figure unit.
  Preparation triggered by a request is charged to the preparation budget (own ceiling), with a
  streamed "preparing units" status. Complex scans may need higher ceilings.
  Guards: per-user daily limits on documents, pages and preparation calls.
LEARNING (per request; every provider retry counts toward the ceiling)
  Summary / quick question       gen 1, review 0 (deterministic only), repair 0   ceiling 2
  Standard concept               gen 1, review 0-1, repair <=1                     ceiling 3
  Revision sheet / detailed unit gen 1-2, review 1, repair <=1                     ceiling 4
  Continue step                  gen 1-2, review 1 (batched), repair <=1           ceiling 4
  Exercise / lab step            gen 1 per <=3 related items, review 1, repair <=1 ceiling 4
  deepen_unit                    gen 1, review 1, repair 0-1                       ceiling 3
  Multi-step run (user asked for several units at once): per-step ceilings plus a request-level
  cap (default 12).
Continue step size: one substantial unit, or up to 3 closely related lightweight units under a
combined weight cap. Never sized by pages or chapters.
Spend priority when the budget tightens: 1 generate essential units, 2 review units with
calculations/numbers, 3 repair essentials, 4 review the rest.
Review need (skip the call when all are false): calculation/derivation, comparison claims, many
numbers, exhaustive depth, exercise kind, any deterministic flag.
Quota: charge the user per request, not per internal call; internal spend is capped by the
budget guard and per-user cost ceilings.
Latency: stream each unit; review unit k while generating unit k+1; limited concurrency, backoff,
circuit breaker.

## Phase 1: Unit Map skeleton and identity (L)
1.1 Heading detection, deterministic first: numbering (I., II.1, 2.b, Exercice N, Question N,
    TP N, Etape N), font size/weight jumps (extend extract-pdf.mjs), header/footer removal.
    Fallback when structure is absent: LLM proposes boundaries per page batch, validated for
    contiguity, no overlap, full page coverage (reuse course_summarizer range checks).
    Roman-numeral structure comes only from the PDF's headings, never from LLM summaries.
1.2 Kind classification per unit (rules, LLM tie-break). A course PDF ending with exercises
    gets exercise units.
1.3 Split oversize units: sub-headings, then figure/table/example boundaries, then page windows.
    Children keep the parent heading_path.
1.4 Identity: logical_id as defined above; content_version computed from unit text + records.
1.5 Reconciliation on reindex: match old to new by logical_id; fallback fuzzy match (title
    similarity + page overlap + text-hash overlap) recorded as explicit rename/split/merge
    mappings. content_version unchanged => keep progress. Changed => status becomes stale
    (kept for reference, regenerated on demand), never carried as explained. Ambiguous split/
    merge => stale, listed in the ledger.
1.6 Store the skeleton after the Course Map in worker.py, versioned by extractor version + text
    hash; backfill job; lazy build on first request if missing.
1.7 Replace the 500-chunk cap with paged index verification.
Exit: skeleton for the course fixture has correct unit boundaries and numbering; reindexing keeps
ids; a heading shifted by one page keeps its logical_id; duplicate "Exemple" headings get
distinct ids.

## Phase 2: Deterministic verifier (build the ruler first) (M)
No LLM. Presence is necessary, not sufficient.
- presence: normalized numbers (0,8593 == 0.8593)
- label binding: a value must appear with its row/column/label path; catches swapped values
- cross-unit label consistency: the same label path must carry the same value everywhere
  (e.g. Mme Benali's fraud probability) against FactsLedger and source records
- structure claims ("partie II = ...") validated against the Unit Map
- provenance gates: valid markers and pages; supplementary values follow the hypothetical rules
- kind contract: required blocks present
- direction check = heuristic tier only (flags, never auto-fails)
- Safe arithmetic evaluator: custom whitelist AST evaluator; numbers, + - * / // % **, unary
  minus, parentheses, a fixed function table (sqrt, log, exp, abs, min, max, round). No names,
  attributes or calls outside the table. Limits on expression length, node count, exponent and
  magnitude, plus a timeout. NEVER eval, exec, sympify or parse_expr on model or PDF strings
  (sympify uses eval internally).
- Statistics/matrix checks use fixed validator functions over parsed numeric arrays, not code.
- Programming exercises: no code execution in v1. If ever needed, a separate sandbox (no
  network, no filesystem, non-root, CPU/memory/time limits) behind its own flag and security review.
Run against the saved baselines first to measure how bad today's output is.

## Phase 3: Preparation and ingestion fidelity (L)
3.1 PageQuality per page (text vs image area, garbled glyph ratio, OCR confidence, table
    alignment). Low-quality pages route to OCR/vision. Items depending on unresolved pages become
    unverifiable_source, never silent gaps.
3.2 Tables: layout-based extraction into header/row records with column-count sanity checks;
    vision fallback on low confidence. Cells become number_table items with label paths.
3.3 Figures: deterministic candidate detection (embedded images/vector charts, captions such as
    Figure/Graphique/Schema, large area, referenced in text), ranked; one bounded vision call per
    selected figure only when text/layout cannot explain it. Output: {type, title, axes, series,
    printed key_values, takeaway, confidence}. Chart-read values are flagged approximate and never
    quoted as exact. Cached by image hash.
3.4 Math: pages with garbled formulas re-extracted via vision into plain/LaTeX records.
3.5 Enrichment (lazy, batched): checklist + prerequisites per 3-5 units per call. Text anchors
    must pass substring validation; failures are dropped and logged. Prerequisite edges
    validated acyclic and in range.
3.6 Preparation jobs are resumable and idempotent: a job table with per-step state
    (pending/running/done/failed), idempotency key (logical_id, content_version, prompt_version,
    step), leases + heartbeats like the worker's existing job claiming, retries with backoff.
    A closed browser or crashed worker resumes at the next undone step; nothing restarts from zero.
3.7 Prefetch: enrich the next unit while the student reads the current one.
Exit (course fixture): waterfall (p.17), beeswarm (p.18), LIME (p.19) and decision tree (p.25)
have figure records with title, axes, takeaway; the p.26 F1 table has 5 correct rows with labels.

## Phase 4: Scope, level, planner, actions (explain_course.py) (M)
- Scope parsing into per-unit flags with reasons ("only part II", "skip exercise 3", "without
  proofs"). Default all. Ambiguity: state the assumption, do not block.
- "What remains" is computed from the skeleton (titles + pages of not_generated in-scope units),
  so exhaustive requests can say precisely what is left.
- Order: source order by default; reorder only to satisfy depends_on. Beginner: at most one primer
  unit (supplementary) for missing external prerequisites. Advanced: list prereqs_assumed, skip
  re-teaching.
- Two distinct actions:
    continue_learning       generates the next not_generated in-scope step in plan order
                            (respecting depends_on), REGARDLESS of earlier partial units
    deepen_unit(logical_id) expands or repairs an existing unit and writes a new UnitVersion
  A partial unit stays flagged but never blocks Continue. Responses carry next_actions[]:
  continue_learning while units remain, plus deepen_unit candidates ranked by the importance of
  their missing items. After the last unit, only deepen candidates remain.
- Request IDs: hash(inquiry, action, logical_id(s), attempt or version).
- Fingerprint = hash(unit_map version, scope), not budget or model. Progress keyed by logical_id.
- LearningState and FactsLedger updated deterministically from verified content, not from the
  generator's self-report.

## Phase 5: Generation (L)
- One generation per unit; tiny related units may share a call; dense units may use two.
- Inputs: the unit's pages, its figure/table records, checklist with importance, depth/level,
  LearningState summary, relevant FactsLedger entries, and a kind-specific prompt.
- Evidence trimming never drops chunks anchoring essential items; if the prompt is still too big,
  split the unit.
- Continuity: the document overview appears once; later units start at their own heading, link
  back to established material, never repeat an introduction, pitfall or check question.
- Prompts: teach each checklist item in order; reproduce source numbers and tables with their
  labels; walk calculations step by step; explain why, not only what; mark source markers on every
  factual sentence; label provenance per block; supplementary content follows the rules above.
- Structured output: reuse structured_output.py truncation recovery per block; on truncation, mark
  remaining items missing and queue repair.
- Schema v2 replaces the card-level definition / intuition / course_example / pitfalls /
  check_question for course and exercise modes.
- Stream the draft as PROVISIONAL (see Phase 7).

## Phase 6: Independent review, repair, consistency (L)
Review call, batched (up to ~4 units), different prompt from the generator and ideally a different
model, with no access to the generator's self-assessment:
- Framing: "find problems", not "grade this".
- Inputs: source anchors + figure/table records + checklist + blocks with provenance and claims +
  the relevant FactsLedger entries.
- Outputs per unit: missing essential/supporting items; unsupported or incorrect claims; cross-unit
  conflicts (definitions, numbers from the same case, notation, capability/limitation claims,
  conclusions), each quoting both sides; pedagogy issues (level mismatch, copy-without-explaining,
  unexplained jargon, calculation without steps) and a 0-3 score; ledger_updates (definitions,
  results, notation, claims) each with a quote.
- Every finding and update must quote the output; a quote that is not a substring is discarded.
  ledger_updates enter the FactsLedger only if the unit has no unresolved authoritative error.
- Authoritative deterministic findings override reviewer opinion; heuristic flags and reviewer
  findings are weighed together. Reviewer judgments are calibrated, not trusted blindly.
Verdict: explained = required items covered AND no unresolved authoritative errors AND (if
reviewed) pedagogy >= 2 AND no open cross-unit conflict. Otherwise partial/mentioned/missing.
Repair: at most 1 targeted call per flagged unit, containing only the findings plus anchors;
merge blocks; re-run Phase 2 gates; re-review only if the budget allows. If a conflict shows an
EARLIER unit was wrong, repair that unit and emit a visible correction (Phase 7), not a silent edit.
Exercises: correctness comes first from the safe evaluator/validators, then the review call.
Calibration: the reviewer must flag the known-bad Part 1/Part 2 baselines and pass a hand-written
good unit; track agreement with your labels per prompt/model version.

## Phase 7: Lifecycle, contract, compat (M)
Unit lifecycle: generating -> checking -> ready.
Events: prep_status, unit_draft (provisional), unit_checking, unit_ready (verified version),
unit_correction (change_log with old/new quotes, reason code, severity).
- Persist every version (provisional, verified, repaired, deepened) with its change log. Replay
  after reconnect returns the latest version plus its corrections. Streamed content is labelled
  provisional until unit_ready. A serious correction carries severity high.
- schema_version 2 with Pydantic models for UnitOutput, UnitProgress, UnitVersion, FactsLedger,
  LearningState.
- Compat serializer also emits the legacy `sections` list (title, markdown, pages) and appends a
  one-line correction notice when a correction exists, so the current UI keeps working without
  hiding corrections.
- Cache unit outputs by (logical_id, content_version, prompt_version, level, depth).
- Every response carries a ledger: coverage counts, verification counts, remaining units (from the
  skeleton), partial units with their missing items and pages, skipped optional items,
  low-fidelity pages, corrections issued, and next_actions.

## Failure handling (bounded fallback for every stage)
- Heading detection fails: LLM boundary fallback; else page windows flagged low confidence.
- Enrichment fails: generate from text with a minimal checklist; mark verification
  deterministic_only; retry enrichment later.
- Vision fails or low confidence: figure becomes unverifiable_source; teach from caption/text
  only; flagged.
- Generation truncated: salvage complete blocks; mark the rest missing; queue repair.
- Review fails or times out: verification review_failed; content kept; high-risk units get
  confidence low and are queued for review.
- Repair fails or returns invalid output: keep the original; list the missing items.
- Budget exhausted: stop with an honest partial ledger; Continue resumes.
- Rate limits: backoff + circuit breaker; retries count toward the budget.
- Reindex changes content: affected units become stale; nothing is silently reused.

## Observability
Per unit: logical_id, kind, pages, chunks sent/dropped, figures used, tokens in/out, calls by
purpose and by budget type (preparation/learning), latency, cost, verdict dimensions, repair
attempts, corrections. Per request: budget used vs ceiling, ledger counts. Golden-eval trend per
prompt/model version.

## Acceptance tests (quality evals, separate from plumbing tests)
Scoped scenarios on the explainability PDF. Each is scored only against its own must-teach list,
and generating units outside the requested scope counts as a failure.
  A. Part II (post-hoc methods, II.1 to II.9). Prompt: "Explique-moi intégralement la partie II,
     de II.1 à II.9, avec les calculs, les graphiques, les exemples numériques et les limites de
     chaque méthode. Ne résume pas : enseigne chaque notion progressivement et indique
     précisément ce qui reste à étudier."
     Must teach: permutation importance, leakage detection, SHAP manual calculation step by step,
     waterfall and beeswarm interpreted from their figure records, LIME, SHAP vs LIME,
     instability, limitations. Must NOT be penalized for omitting page 26 or auditability.
  B. Part III (interpretable models + performance comparison, p.23-26): p.26 F1 values bound to
     the right model labels, the log-transformation effect, the performance/interpretability
     trade-off reasoning.
  C. Part IV (auditability): Mme Benali decision reconstruction, the auditability chain, DVC,
     MLflow, Model Card, TP07 checkpoints.
  D. Whole document: A + B + C + Part I; the ledger honestly lists anything not generated.
  (Confirm the Roman numerals against the PDF's own headings before finalizing A to D.)
Behavior tests
- continue_learning after a partial unit advances to the next unit; it does not repeat it.
- deepen_unit repairs the partial unit and writes a new version.
- Reconciliation: heading shifted one page keeps logical_id and status; changed content becomes
  stale; duplicate "Exemple" headings get distinct ids; a split/merge is recorded.
Safety tests
- "9**9**9" and oversized expressions are rejected; no model or PDF string is ever eval'd.
- A PDF containing "ignore previous instructions" text has no effect on any stage.
Correctness tests
- Seeded "F1 augmente de 0,8669 à 0,8593" is flagged (heuristic) and caught by the reviewer.
- Mme Benali's probability stated as 0.942 in one unit and 0.924 in another is caught
  deterministically.
- Seeded swapped structure sentence (II = interpretable models) is caught against the Unit Map.
- Unsupported second sentence inside a `course` block is found at claim level and corrected or
  moved to supplementary.
- Supplementary "10 imaginary students" example passes; a hypothetical reusing a source label with
  a different value fails.
- Seeded cross-unit contradiction (SHAP described as exclusively local) is flagged and repaired
  with a visible correction on the earlier unit.
Lifecycle and failure tests
- Reviewer finds an error after the draft streamed: unit_correction emitted with old/new quotes;
  version history persisted; replay shows the corrected version plus the correction.
- Reviewer down: verification review_failed; high-risk unit confidence low and queued.
- Preparation job killed midway: resumes without redoing completed steps.
- Budget exhausted: honest partial ledger and a working Continue.
Other documents
- KNIME lab: every step, command/UI action, checkpoint, deliverable present.
- Exercise sheet: every (sub-)question has a final answer; numerics validated; "skip exercise 3"
  respected; dependent questions use earlier results.
- Maths chapter: derivation steps ordered and validated.
- Grammar lesson: sourced examples; no invented "course examples" labelled `course`.
- Research paper: figures/tables described; limitations covered.
Reviewer calibration: flags the negative controls, passes the positive control.
Metrics per run: essential coverage %, correctness errors, pedagogy score, calls used by budget
type, latency, cost.

## Risks and decisions
- Heading detection on scans/odd layouts: OCR + LLM fallback, mark unverifiable, do not guess.
- Vision reads are approximate: flagged, never quoted as exact.
- Cost: a 9-unit exhaustive scope is roughly 8-14 learning calls plus batched preparation;
  mitigated by batching, lazy enrichment, caching, and user-triggered steps.
- Reviewer leniency or shared blind spots: adversarial framing, quote-validated findings,
  deterministic authority for sound rules, a different model where possible, human-label calibration.
- Open: importance heuristics need tuning on the golden set.
- Open: defaults for Continue step size and ceilings are starting values to calibrate.
- Open: sequential vs parallel unit generation; start sequential, overlap review only.
- Deferred: front-end display of units, provenance chips, correction history, wording of
  "Explained" vs "Reviewed".
- Deferred: any code execution for programming exercises.

## Build order
0 -> 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> 7 -> rollout
Rollout: flag EXPLAIN_UNIT_PIPELINE (default off), shadow mode on the golden set, calibrate
budgets from measurements, enable in order course, lab, exercise, other; remove the legacy path
after two clean eval runs.
Phases 0 to 2 come first on purpose: build the ruler before the thing it measures.
